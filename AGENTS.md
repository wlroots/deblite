# AGENTS.md

Guidance for AI coding agents and human contributors working on the DebLite
ISO repository. `CLAUDE.md` is a symlink to this file. Keep both in sync by
editing only this file.

User documentation lives in [`README.md`](README.md). Build and release details
live in [`docs/BUILD.md`](docs/BUILD.md) and [`docs/CI.md`](docs/CI.md).

## What this repository is

DebLite builds four lean Debian 13 (Trixie) live ISOs with `live-build`:
KDE Plasma, GNOME, XFCE and Cinnamon. Each ISO boots into a live session and
ships a custom installer. The installer source lives in the separate
[`deblite-installer`](https://github.com/deblite/deblite-installer)
repository; this repository downloads a pinned `.deb` release and installs it
into the live root filesystem.

`arch-installer/` is a reference implementation for Arch. It is not built,
installed or shipped. Leave it alone unless the task explicitly concerns it.

## AI-assisted contributions

Using AI is allowed. It is not prohibited, and no disclosure is required. The
result is what matters, and the result must be clean:

- You are responsible for every line you commit. Do not submit generated code
  or prose you cannot explain and defend.
- Read the surrounding code and docs first. Match existing patterns instead of
  inventing new ones.
- Keep diffs minimal and focused. No drive-by reformatting, renames, dependency
  bumps or unrelated "improvements".
- Never fabricate test results, checksums, release assets or URLs. If you did
  not run a check, say so explicitly.
- Do not commit secrets, tokens, private keys or machine-specific paths.
- Do not add "Generated by ..." footers, badges or author tags unless asked.
- Respect the licenses of code, packages and assets you bring in.

The same review bar applies to AI-assisted and human-written changes.

## Non-negotiable project invariants

These are product requirements, not preferences:

- **Lean by default.** `live-build` runs with `--apt-recommends false` and
  `--no-install-recommends --no-install-suggests`. Never enable recommends or
  suggests.
- **No bloat.** `scripts/audit-bloat.sh` fails the build for LibreOffice,
  Thunderbird/Evolution, GNOME Software, GNOME games and similar packages. Do
  not add them, their meta-packages or dependencies that drag them in.
- **Four editions only:** `kde`, `gnome`, `xfce`, `cinnamon`. The
  `gnome-backports` flavor is scaffolded and dirty-gated; do not add it to the
  CI matrix or publish it.
- **Every edition ships** Neovim, GIMP, Helium, ONLYOFFICE Desktop Editors and
  `firewalld`. `scripts/verify-iso.sh` enforces this.
- **No Debian installer and no Calamares.** The live-build invocation uses
  `--debian-installer none`, and the verifier rejects their files.
- **The installer is external.** Never copy `installer/` sources back into this
  repository. Builds consume `deblite-installer` from a pinned release.
- **Installer downloads are verified.** `scripts/fetch-installer-deb.sh` must
  validate the `.deb` against the release `SHA256SUMS` (or
  `DEBLITE_INSTALLER_SHA256`) before it is placed in `packages.chroot`.
- **Root filesystem is copied, not bootstrapped.** The installer unsquashes the
  live `filesystem.squashfs`; it does not use `debootstrap`, `pacstrap` or
  network installs.
- **Erase-disk only.** The installer currently supports a single `erase_disk`
  mode. Do not document or imply alongside/manual partitioning.
- **Unsigned GRUB, no Secure Boot.** The ISOs and installed systems use
  unsigned GRUB. Do not claim Secure Boot support without wiring
  `shim-signed` and testing it.
- **GitHub assets stay below 2 GiB.** Release builds use xz and enforce the
  limit. Do not remove the guard or publish an oversized ISO.
- **Reproducible inputs.** Third-party packages and installer `.deb` files
  enter the build through the documented fetch scripts and pinned metadata,
  not through ad-hoc downloads or committed binaries.

## Repository map

| Path | Purpose |
|---|---|
| `config/common/` | Shared package lists, hooks, includes and live-build preseed |
| `config/flavors/<name>/` | Per-edition packages, theming and autologin |
| `scripts/build-iso.sh` | Main ISO build; re-executes itself with `sudo` |
| `scripts/fetch-installer-deb.sh` | Downloads and verifies the pinned installer |
| `scripts/fetch-vendor-debs.sh` | Vendors Mint theme packages for Cinnamon |
| `scripts/verify-iso.sh` | Static checks for required/forbidden ISO contents |
| `scripts/audit-bloat.sh` | Rejects explicitly excluded packages |
| `scripts/test-install.sh` | Installs an ISO to a loop image and checks it |
| `scripts/qemu-smoke.sh` | Boots the live kernel/initramfs in QEMU |
| `scripts/check-debian-release.sh` | Detects new Debian 13 point releases |
| `installer-release.env` | Pinned installer repo/version/checksum |
| `debian-version.txt` | Debian 13 point release baked into manifests |
| `.github/workflows/` | CI, ISO matrix, release publishing, Debian watcher |
| `docs/` | Build, CI and flavor documentation |
| `out/`, `build/` | Ignored build output; never commit them |

## Commands

Run these from the repository root. Build and install tests need root.

```sh
make check                                      # shellcheck all scripts
./scripts/fetch-installer-deb.sh --output /tmp/installer.deb
sudo ./scripts/build-iso.sh xfce                # zstd, development build
sudo ./scripts/build-iso.sh kde --release       # xz + 2 GiB guard
sudo make all                                   # all four release ISOs
./scripts/verify-iso.sh out/deblite-13-xfce-amd64.iso
./scripts/audit-bloat.sh out/deblite-13-xfce-amd64.iso
sudo ./scripts/test-install.sh out/deblite-13-xfce-amd64.iso --boot
./scripts/qemu-smoke.sh out/deblite-13-xfce-amd64.iso
```

For offline work, skip the download with a locally built installer package:

```sh
DEBLITE_INSTALLER_DEB=/path/to/deblite-installer_0.1.0_amd64.deb \
    sudo -E ./scripts/build-iso.sh xfce
```

`DEBLITE_INSTALLER_BASE_URL` can point at a mirror (or a `file://` directory)
to exercise the download and checksum path without publishing a release.

## Testing expectations

Run the checks that match the change, and report exactly what ran:

| Change | Minimum verification |
|---|---|
| Shell script, docs, workflow text | `make check`, plus YAML parse for workflows |
| `config/common/` | Build one edition, then `verify-iso.sh` and `audit-bloat.sh` |
| `config/flavors/<name>/` | Build that edition, then verify and audit |
| Installer pin or fetch logic | Fetch the `.deb`, build one edition, verify and audit |
| Boot, GRUB, rootfs or de-live logic | Above plus `test-install.sh --boot` and `qemu-smoke.sh` |
| Partitioning, LUKS or filesystem logic | `test-install.sh --luks` and manual UEFI/BIOS VM boot |

Notes:

- `scripts/test-install.sh` uses loop devices and must not touch a real disk.
  It intentionally forces the BIOS layout so it cannot write host NVRAM.
- Test UEFI boot and the GRUB menu in a VM. Do not run UEFI install tests on a
  development host.
- `--boot` and `qemu-smoke.sh` need `qemu-system-x86_64`; KVM speeds them up
  but is not required.
- Workflow YAML can be parsed locally when PyYAML is available, but only CI
  proves the workflow. Be conservative with permissions and action versions,
  and match the existing workflows.
- A full ISO build takes tens of minutes. If you skip it, state that the ISO
  was not rebuilt and that `verify`/`audit` were not run.

## Change workflow

1. Read the relevant script, config and docs before editing.
2. Make the smallest change that satisfies the request.
3. Update documentation and comments when behavior, flags or pins change.
4. Run the verification above.
5. Check `git status` for stray artifacts (`out/`, `build/`, `*.deb`, ISOs)
   and leave the tree clean.
6. Commit focused changes with an imperative subject line, for example
   `Fix the XFCE screen locker package` or `Pin installer 0.2.0`.

Do not silently mix unrelated changes in one commit. Do not rewrite history or
force-push unless the user explicitly asks.

## Code style

### Shell

- `#!/usr/bin/env bash` and `set -euo pipefail`.
- Quote variables, use `local` in functions, prefer `$(...)` over backticks.
- Provide `-h`/`--help`, reject unknown arguments with exit code `2`.
- Put actionable messages on stderr; use `FAIL:`/`error:` consistently.
- Keep scripts `shellcheck` clean. Do not disable a check without a comment
  explaining why.
- Resolve paths from `BASH_SOURCE`, not the caller's working directory.
- Never run destructive commands against a real disk. Loop devices only.

### Python

This repository should not contain production Python. If a task requires it,
follow the `deblite-installer` conventions: Ruff, 100-column lines, type hints,
small functions and `pytest` coverage.

### Configuration and packages

- Keep package lists grouped and commented by purpose.
- Add the smallest package that provides the feature; avoid meta-packages.
- Never add a package without checking that its recommends/suggests do not
  pull in blocked software.
- Keep `config/common` free of edition-specific choices; those belong in
  `config/flavors/<name>/`.
- Preserve the no-recommends apt policy in `99deblite`.

### Documentation

- `README.md` is for end users: installation, first boot, troubleshooting.
  Keep build details in `docs/`.
- Use fenced code blocks, relative links for repository files and full URLs for
  external resources.
- Do not invent screenshots, download links, version numbers or feature claims.
- Wrap prose at roughly 80 columns, matching the existing docs.

## Installer changes

The installer is a separate repository. Do not patch it from here.

- Source: <https://github.com/deblite/deblite-installer>
- Local sibling checkout for development: `../deblite-installer`
- Tests there: `make test`, `make lint`, `make deb` (Ruff, pytest, shellcheck)
- Release tags: `installer-vX.Y.Z`, matching `installer/__init__.py` and
  `pyproject.toml`.
- To consume a new installer: publish the release in that repository, then bump
  `DEBLITE_INSTALLER_VERSION` in `installer-release.env` here and rebuild.
- Keep `installer-release.env` honest. Do not point it at a tag that has not
  been published; CI downloads the pinned release on every push.

## Releases

- ISO tags are `v13.X`, matching `debian-version.txt` and the Debian point
  release. The daily watcher updates the file, tags, and dispatches the build.
- Pull requests build zstd ISOs without publishing. Tags and manual
  `release=true` runs build xz ISOs and publish a GitHub Release.
- Release assets are the ISO, its `.sha256` and `.manifest.json`, plus the
  installer `.deb` and `SHA256SUMS` in the installer repository.
- Do not publish or delete releases as part of a normal code change.

## When in doubt

Ask before making destructive or irreversible changes: repartitioning logic,
LUKS handling, disk selection, release deletion, history rewrites or anything
that could write to a host disk or NVRAM. Guessing is worse than pausing.
